# Тестовые сценарии humanized

В каждой папке лежит входной текст и запрос с критериями в `checks.md`. Сценарии для модели проверяются вручную. Ожидаемые результаты линтера для всех входов и пограничных случаев проверяет отдельный тест.

```bash
python3 -B plugins/humanized/evals/test_lint.py
```

## Как прогнать сценарий

1. Откройте новую сессию в пустой временной папке, чтобы в контексте не было этого репозитория и прошлых разговоров. Для Claude Code путь к плагину замените на свой:

```bash
cd "$(mktemp -d)" && claude --plugin-dir /path/to/turbo-bullfinch/plugins/humanized
```

Для Codex сначала установите скилл по инструкции в [README плагина](../README.md), затем запустите новую сессию `codex` в пустой временной папке и явно вызовите `$humanized` в запросе. Для другого агента установите тот же каталог скилла и используйте его способ вызова. Фактический запуск линтера зависит от доступа агента к shell и Python.

2. Отправьте запрос из checks.md, а под ним текст из input.md без изменений.
3. Сохраните ответ в out.md рядом со входом. Файлы out*.md в git не попадают.
4. Прогоните линтер на входе и на ответе из корня репозитория.

```bash
python3 plugins/humanized/skills/humanized/lint.py plugins/humanized/evals/01-inflation-triads/out.md
```

5. Пройдите по checks.md построчно и отметьте каждую проверку.

Сценарий 09 состоит из трёх прогонов, по одному на вход, и каждый идёт в новой сессии.

## Что считать провалом

Сценарий провален, если не выполнена хотя бы одна проверка из checks.md. Провалом считается и то, что в проверках не названо: в ответе появились факты, числа или имена, которых не было во входе; изменён код, цитата или текст вне запрошенного куска; линтер вернул ненулевой код там, где checks.md ждёт 0. Если линтер на входе нашёл не то, что записано в checks.md, сломан вход или линтер, и сценарий нужно сначала починить.

## Слепое сравнение версий

1. Соберите отдельную подборку русскоязычных черновиков. Включите рабочие треды, письма клиентам, личные посты и резюме, а также удачные тексты, которым правка не нужна. Используйте одинаковые вводные, включая образец авторского голоса, если он есть.
2. Для каждого запроса получите ответ с текущей и новой версиями скилла в двух чистых сессиях. Зафиксируйте модель, её настройки и доступ к инструментам. Случайно поменяйте порядок двух вариантов в каждой паре. Покажите каждому читателю одну и ту же исходную задачу и черновик без названий версий.
3. Попросите нескольких читателей независимо выбрать более естественный вариант в заданной ситуации или отметить ничью. Отдельно запишите соответствие жанру, сохранение голоса и случаи, когда читатель предпочёл исходный текст обеим правкам.
4. Сверьте обе версии с исходником. Посчитайте добавленные или потерянные факты, изменения условий и степени уверенности, нарушения границ правки и лишние вмешательства в удачные исходники. Сообщите число пар, предпочтения и ничьи по жанрам и число смысловых ошибок для каждой версии.

Сравнение поддержит изменение, если новая версия выигрывает по естественности, сохраняет факты и голос автора и реже вмешивается в удачные тексты. На малой выборке указывайте абсолютные числа.
